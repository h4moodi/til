# Sender-Constraining OAuth Tokens with DPoP

*Cryptography, authentication & identity · 2026-11-21*

## What it is

DPoP (RFC 9449) turns a bearer access token into one that only works alongside a key the client holds. The client creates an asymmetric keypair, and for every request it signs a short JWT (the *DPoP proof*) covering the HTTP method, the URL and, at resource servers, a hash of the access token. The authorization server writes the key's JWK thumbprint into the token (`cnf.jkt`), so a token lifted from logs, a proxy or a compromised SPA store can't be replayed without the private key.

## Example

Proof JWT (header . payload, signed with the client's private key):

```json
{ "typ": "dpop+jwt", "alg": "ES256", "jwk": { "kty": "EC", "crv": "P-256", "x": "…", "y": "…" } }
{ "jti": "e1j3V_bKic8-LAEB", "htm": "GET", "htu": "https://api.example.com/orders",
  "iat": 1795500000, "ath": "fUHyO2r2Z3DZ53EsNrWBb0xWXoaNy59IiKCAqksmQEo" }
```

- `typ`/`jwk`: marks it as a DPoP proof and carries the public key (never a private one).
- `jti` + `iat`: unique ID and timestamp, so the server can reject replays within a short window.
- `htm`/`htu`: binds the proof to one method and URL (no query string or fragment).
- `ath`: base64url SHA-256 of the access token, tying the proof to *this* token.

```bash
curl https://api.example.com/orders \
  -H "Authorization: DPoP $ACCESS_TOKEN" \
  -H "DPoP: $PROOF_JWT"
```

The scheme is `DPoP`, not `Bearer`, and the token response says `"token_type": "DPoP"`.

## When to use it / why it matters

- **Defensive:** this is the main option for public clients (SPAs, mobile, CLIs) that can't do mTLS-bound tokens (RFC 8705). It's also required in FAPI 2.0 profiles. Store the key as non-extractable (WebCrypto `extractable: false`, or the platform keystore) or you've just moved the secret.
- **Resource-server checklist:** the signature verifies against the embedded `jwk`; its thumbprint equals the token's `cnf.jkt`; `htm`/`htu` match the actual request; `ath` matches; `iat` is fresh; `jti` hasn't been seen. Accepting `Authorization: Bearer` for a DPoP-bound token throws away all of this.
- **Server nonces:** respond with `use_dpop_nonce` and a `DPoP-Nonce` header to defeat proofs pre-generated by an attacker with brief code execution in the client.
- **Pentest angle:** replay a captured token with `Bearer`, with no proof, with a proof for another URL, or with a reused `jti`. Each one that works is a finding. XSS that can call the signing key still mints proofs live, so DPoP limits theft, not session riding.
